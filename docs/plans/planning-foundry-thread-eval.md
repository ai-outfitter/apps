# Planning and Software Foundry from request to morning follow-up

Proposed local acceptance evaluation, November 25, 2026. The [first installed replay](../../apps/software-foundry/agent-evals/planning/README.md#keystone-request-to-personal-home) covers the Keystone request through personal Home. The remaining stages address two broader questions. Can a member choose which release deserves a request using real Planning and repository evidence? Can that member leave the app and resume the same work from a native conversation the next morning?

## Fixture and decision under review

Use the real Keystone feature request in disposable repositories. **Keystone** lets operators install services on their own infrastructure from iOS and macOS. **Chart Studio** helps analysts author charts. They share a chart library but have different users, promises and success measures. Give Keystone a four-week project, “Install Forgejo and Grafana from the native apps,” with a dated service installation demo and two actual project-linked Release revisions, “Pilot” and “Team rollout.” Seed one unrelated active Chart Studio project and an archived lookalike. Record product brief/revision, project goal and interval, release scope, acceptance criteria, dependencies, owner and evidence as inspectable fixture records. Preserve the existing synthetic Forgejo pair for repository evidence. A shared repository alone cannot identify a product.

Proposed decision rule, applied in order. Require accessible product evidence and a project goal that the request advances. Record which users benefit and cite the exact records. For the selected project compare acceptance impact, urgency, effort/dependencies and remaining time against the current release scope. If a missing fact could change the allocation, ask one answerable question. Return a ranked choice with the strongest alternative, rationale and sources. Avoid scoring urgency from the requester's adjectives. Freeze the inputs, rubric version and revisions so two runs can be compared.

| Synthetic request | Expected recommendation and choices |
|---|---|
| Canceling an install still changes the cluster | Current Pilot. Cancel without mutation is an explicit demo criterion. Cite bug evidence, product promise and pilot criterion. Ask the member to accept the fix now or record a reason to move it. |
| Install Forgejo and Grafana from iOS and macOS with standard dashboards | Pilot if both platforms and standard dashboards are pilot acceptance criteria. Team rollout is plausible if the first pilot covers only one platform. Ask “Does the pilot need both iOS and macOS, or can the second client follow in Team rollout?” Show both dates, expected cost and impact on the pilot. |
| Custom chart palettes | Chart Studio fit, weak Keystone fit. Offer routing to the correct product for review or defer unallocated. Do not invent a release. |
| “Improve sync” without a reproduction or user | Needs research. Ask for affected product, failing workflow and deadline. No placement or execution. |

Grade semantic outcomes, valid citations and contradictory evidence handling. Allow another placement only if supported by a changed fixture fact or explicit member rationale. A strong product fit can still miss this project's window. Future release maps to deferred plus the linked release when supported, and unallocated defer maps to backlog. Do not encode a future milestone as current-release. A feature/bug classification selects the Foundry planning lens and does not decide urgency.

## Member journey and its observable effects

1. In the proposed macOS or iOS thread-first experience the member starts a Foundry thread and asks “Can I install Forgejo and Grafana from the Keystone iOS and macOS apps and get our standard Grafana dashboards?”. Foundry lists that persistent work thread beside “Canceling an install still changes the cluster.” Capture distinct IDs and resume each from a second client after closing the first. Resolve the same work ID, repository plan, messages and pending decision even when titles collide. Browser/sidebar fallback remains a valid contract exercise. Record native interaction separately until both clients actually pass.
2. Foundry retains the repository plan, then proposes a Planning intake linked to the work thread and the same request. Planning reads both products, the goal, project window and linked releases through the installed contracts. One app subscription may deterministically handle an explicitly selected event. Another may ask a model whether an ambiguous event is relevant, recording the model version, cited input, result and reason. A declined subscription leaves an inspectable receipt. For an accepted event, open at most one authorized child thread or workflow per subscriber/purpose. Neither a model decision nor a chat reply can expand grants.
3. A request for release choice appears in **this member's main conversation in this organization**. That private conversation is distinct from the shared installation main and from personal Home. Give a second member their own org main, and put the first member in another org. Only the intended recipient sees the question. Link the work, proposed alternatives and decision revision. Await a durable reply across restarts. The answer “Team rollout” updates the pending decision once, records the authorized release-fit write and projects a concise decision reference back to the originating Foundry work. Keep conversational text in its source. Shared contexts receive only domain facts authorized for their audience.
4. Confirm the future choice leaves the work parked. Advance the simulated project to Team rollout, reread revisions and obtain a separate authorized selection for execution. Preview and submit the implementation package only when the member selects it for execution. For a ship run use a disposable synthetic change, approved implementation, reviewed PR, merge and a separately verified tagged release or deployment receipt according to the selected ship criterion. Link the release, commits and work. Keep an unshipped merged control and a second open decision in parallel.
5. Advance the fixture clock over local midnight. In personal Home ask **“What shipped yesterday?”** Return the authorized release, its date/time and links to work and release evidence. Ask “Which product goal did it advance?” from the same Home thread and follow the links under the current viewer. Present pending release questions separately. A late producer wakes or durably re-enqueues a dependency keyed by source/date/revision. Redelivery updates that day's brief without a second shipment. On missing evidence show incomplete coverage. A short polling window, a canned transcript or a pinned morning answer cannot pass.

## Independent checks and retained evidence

| Fault or boundary | Required observation |
|---|---|
| Invalid/missing anchor, partial source coverage, app or bot denied create | Preflight fails before dispatch. Opt-out still works with read-only repositories. A copied marker from another author never suppresses unrelated work. Lost HTTP 201 plus failed first reconciliation resolves to one real planning issue. |
| Concurrent requests, same title, duplicate/reordered inputs, reused key with changed content | Read by stable ID. Identical inputs recover one receipt. Conflicting reuse is rejected or explicitly surfaced. No branch, PR or implementation before selection. Count every repository before and after each stage. |
| Duplicate event, answer before pending projection, crash after applying write before acknowledgment | Record event ID, causal parent, origin, subject revision, target scope, subscriber and outcome. Persist or reconcile pending work. Deliver one logical prompt, one applied decision and one linked child. Ignore stale revisions, prevent loops and show the conflict when two answers race. |
| Model rejects, times out or proposes the wrong organization | Record decline or retryable failure, no silent accept or empty success. Deterministic subscribers require no inference. A subscription, source link or tool suggestion cannot authorize another principal. |
| Spoofed source, forged child link, cross-install replay, read-only user, membership revoked mid-flow | Fail at write/read time. Compare lists, search results, entries, attachment reads and deep links for each principal. Plant unique private canaries and assert none appear in another thread's prompt, payload, summary, attachment or trace exported for sharing. |
| Merge without release, event twice, release exactly at midnight, delayed producer, two authorized orgs and one inaccessible | Count each authorized shipped release once in its local day. Never conflate a proposal, accepted decision, merged-only change or pending task with a shipment. Preserve revision lineage; reopen from saved links. |

## Decisions for review

1. Should the first replay use existing Release revisions as the selectable planning horizon, or must it support separately dated milestones within one Release? The latter requires an explicit mapping and product contract.
2. Is a member-confirmed recommendation the default for all release allocations, or may a deterministic policy accept documented low-risk fits? The first replay assumes member confirmation and independent delivery authorization.
3. When a request fits a different product, should Planning suggest rerouting or create a child intake immediately after approval? The worked palette case assumes suggestion first.
4. Should a resolved release choice expose only disposition and release link to shared work, or also a member-approved rationale? Default to the first, with viewers reauthorized on link open.
5. Is a tagged published release sufficient for “shipped,” or must a particular deployment target accept that revision? Pick one observable criterion for the passing case and preserve the merged-only negative.
6. Should Home aggregate organizations by the viewer's local calendar interval or reproduce each producer's reporting day? The proposed member-facing answer uses the viewer's interval and marks insufficient timestamp coverage. Should a late release revise the saved brief, append a correction, or both?
7. Which native milestone is required on first delivery: working thread identity/links across both clients, or also background notifications and offline reply synchronization? Only the former is assumed in the proposed native grade.
